# Пользовательские сценарии и e2e-проверки

Интеграционные e2e-тесты запускают **реальную связку frontend + backend** в
браузере Chromium (Playwright). Бронирование не мокается: тест выбирает слот из
ответа `/event-types/{id}/slots` и создаёт запись через
`POST /event-types/{id}/bookings`.

## Запуск

```
# один раз: скачать браузер Chromium (зависимость только для e2e)
cd frontend && npx playwright install chromium

# запуск e2e (сам поднимает backend на :8000 и frontend на :5173)
cd frontend && npm run test:e2e

# Playwright UI (пошаговый отладчик тестов)
cd frontend && npm run test:e2e:ui

# просмотр HTML-отчёта после прогона
cd frontend && npm run test:e2e:report
```

Playwright поднимает оба сервиса сам (`webServer` в `frontend/playwright.config.ts`)
и ждёт их готовности. Перед локальным прогоном лучше остановить старые процессы:

```
ps aux | grep -E "uvicorn|vite"
```

Если порт `5173` занят старым Vite, приложение не встанет на 5173, а бэкенд
разрешает CORS только для `localhost:5173` — тесты будут падать. Убейте старые
процессы или перезапустите frontend через Playwright.

## Предусловия

- Okno бронирования: сегодня + 14 дней; шаг сетки слотов — 30 минут.
- Рабочее время владельца по умолчанию: Пн–Пт 09:00–18:00 (таймзона владельца
  `Europe/Moscow`).
- В backend при старте засеяны три типа событий («Пятнадцатиминутка», «Полчаса»,
  «Обзор проекта») — тесты всегда выбирают первый доступный.
- Бэкенд хранит данные в памяти: на каждом чистом запуске (в CI — каждый job)
  данные девственно чистые.

## Основной успешный сценарий бронирования

| # | Шаг пользователя | Ожидаемый результат |
|---|------------------|---------------------|
| 1 | Открывает приложение (`/`) | Видит шаг «Что за встреча» и карточки типов событий |
| 2 | Выбирает первый тип события | Появляются шаг «Когда» (даты + часовой пояс) и сетка слотов |
| 3 | Выбирает первый день с доступным временем | В сетке видны свободные слоты (роль `option`) |
| 4 | Выбирает первый свободный слот | Появляется шаг «Ваши данные» с формой брони |
| 5 | Вводит имя (обязательное поле); email/телефон можно оставить пустыми | Поле «Имя» заполнено, форма готова к отправке |
| 6 | Нажимает «Записаться…» | POST → 201; появляется секция «Вы записаны» с временем, таймзоной и именем гостя |
| 7 | Открывает `/owner` и вкладку «Брони» | Новая бронь видна в таблице броней с именем гостя |

## Сценарий проверки обязательного поля

| # | Шаг | Ожидаемый результат |
|---|-----|---------------------|
| 1 | Добраться до формы брони (те же шаги 1–4) | Форма видна |
| 2 | Оставить поле «Имя» пустым и нажать «Записаться…» | Валидация не пропускает: показывается «Укажите имя», `aria-invalid="true"` |
| 3 | — | Секция «Вы записаны» не появляется, бронь не создаётся |

## Изоляция и очистка тестовых данных

- **Уникальные имена гостей**: каждый тест генерирует `e2e-<timestamp>-<rand>`,
  поэтому повторные прогоны не конфликтуют и легко ищутся в списке броней.
- **Динамический выбор слота**: тест берёт первый свободный день и первый
  свободный слот из реального ответа API, а не жёстко заданные дату/время.
- **Порядок**: `workers: 1` и `fullyParallel: false` — тесты идут строго
  последовательно, один процесс бронирования не «съедает» слот второго.
- **CI**: backend создаётся заново в каждом job (in-memory хранилище), поэтому
  между запусками нет общего состояния.
- **Локально**: Playwright по умолчанию переиспользует уже запущенные сервисы
  (`reuseExistingServer`, отключается в CI). Чтобы получить чистое состояние —
  перезапустите backend/убедитесь, что локальный прогон использует свежий
  экземпляр, либо остановите uvicorn перед запуском.

## Артефакты при падении

- screenshot: только при падении;
- video: сохраняется при падении;
- trace: сохраняется при падении (`.zip` в `frontend/test-results/`);
- HTML-отчёт: `frontend/playwright-report/index.html`.

В CI эти артефакты выгружаются как GitHub artifacts.
